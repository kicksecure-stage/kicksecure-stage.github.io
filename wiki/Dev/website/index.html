Server forcing browser cache clear methods

DEV

  • As discussed with admin a method for forcing the browser to reload a document by the server is needed - especially for the mobile browsers. They sometimes don't even reload the document, but just the headers and they seem to ignore or misinterpret our cache headers
  • Suggestions: Admin could use
    • cache-control: no-store : This would be a very aggressive anti cache strategy that prevents any caching. It's maybe too aggressive, but mentioned for completeness
    • cache-control: no-cache, must-revalidate : no-cache does not prevent the use of caching, but forces the browser to revalidate with the origin server
    • ETag: [versionId] : The Etag header could be used. This is basically a version number header for the document
  • Opinion
    • We are currently using: cache-control: s-maxage=86400, must-revalidate, max-age=0
    • Dev thinks that we are missing the no-cache value. This should be tried first. All the big platforms seem to have it https://fred-gu.medium.com/fix-the-annoying-web-page-caching-issue-permanently-5d16527d0b5a
    • ETag also seems like an interesting method. The article above does not mention ETag, but it might be there. But browsers could also ignore ETag
    • No-store seems too aggressive and can maybe only be used if the request has the ?debug=true query. But on the other hand our developer bypasses are good enough Dev thinks
  • For more information
    • https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control
    • https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/ETag

    • Problem Description
      • Proof of concept : test B4 on CSS Extension Fork demonstrates the bypass: {{#css:/src-copy/%2e%2e/%2e%2e/COPYING}} produces a valid <link> tag instead of the expected "Invalid/malicious path" error.
      • In detail: The CSS Extension's path sanitizer fails to decode URL-encoded characters before performing security checks. The function cssRender() in hooks.php currently decodes only %2f (slash) and %5c (backslash) via str_ireplace(), but does not decode other percent-encoded characters like %2e (dot). This allows an attacker to bypass the path traversal protection by encoding .. as %2e%2e. The subsequent urlUtils->expand() check then evaluates the still-encoded path, which does not contain literal .. sequences, and therefore fails to detect the traversal attempt. Although nginx correctly decodes the URL when serving the request, the CSS Extension should block such paths at the application level before they reach the web server.
    • Recommended Fix :
      • Add rawurldecode() to the path variable at the beginning of the file-based CSS branch in cssRender(), before the existing str_ireplace() calls. This ensures all percent-encoded characters are decoded prior to path normalization and security checks.
      • AI Prompt for Code Fix: The following PHP code from a MediaWiki extension has a security vulnerability:

URL-encoded path traversal via %2e (dot) is not detected because only %2f and %5c are decoded before path validation.

File: hooks.php, method: cssRender() Location: The "Regular file" branch, approximately line 130-140

Current code snippet: $path = str_ireplace( '%2f', '/', $css ); $path = str_ireplace( '%5c', '\\', $path ); $path = str_replace( '\\', '/', $path );

Add rawurldecode() to decode ALL percent-encoded characters before these replacements, so that %2e becomes '.' and the subsequent urlUtils->expand() check can detect path traversal attempts. The fixed code should decode the path first, then apply the existing replacements and validation.

Please provide the corrected PHP code snippet with a comment explaining the fix.
